## 1. 产品定位与边界定义

### 1.1 产品定位

**DataHub 是基于现有 Spider 采集系统演进而来的企业级通用数据中台**，覆盖数据采集、治理、存储、服务、应用到运维管控的全链路。

核心价值主张：
- **不推倒重来**：在 Spider 现有 采集 → 下载 → 同步 → ETL 链路上扩展，保护已有投资
- **多源接入**：从单一爬虫采集扩展到 API、文件上传、数据库同步、日志采集四类数据源
- **数据资产化**：通过治理体系将原始数据转化为可理解、可信任、可复用的数据资产
- **服务化输出**：通过数据 API 和指标平台，让数据以服务形式参与业务

### 1.2 产品边界

| 在范围内 | 不在范围内 |
|---------|-----------|
| 数据采集（爬虫/API/文件/DB同步） | 业务系统开发（ERP/CRM 自身） |
| 数据治理（质量/元数据/血缘/权限） | 机器学习模型训练平台（仅提供数据 feeds） |
| 分层存储（ODS/DWD/DWS/ADS/DIM） | 底层基础设施运维（K8s/网络） |
| 数据服务（API/指标/报表） | 数据可视化引擎开发（集成第三方） |
| 任务调度与监控 | CI/CD 流水线 |
| AI 辅助（SQL/模板/Dashboard） | AI 模型训练框架 |

### 1.3 与现有 Spider 系统的关系

```
现有 Spider 能力                    DataHub 扩展能力
──────────────────                 ──────────────────
✅ 模板化采集（YAML 模板）           → 保留，作为采集层的一种 adapter
✅ 站点适配器机制                     → 保留，扩展为通用数据源适配器
✅ 反爬（代理/延迟/身份轮换）          → 保留
✅ 采集 → 下载 → 同步 → ETL 链路     → 保留核心链路，扩展 ETL 分层
✅ MongoDB/Redis/MinIO/Kafka/PG     → 保留，新增冷热分层策略
✅ AI 辅助（SQL/Dashboard/模板）      → 保留，扩展为 AI Copilot
✅ React + FastAPI 管理界面          → 保留，扩展为数据中台管理门户
❌ 多源接入（API/文件/DB同步）         → 新增
❌ 元数据管理与血缘追踪               → 新增
❌ 数据质量管控体系                   → 新增
❌ 数据 API 服务化                   → 新增
❌ 指标平台                          → 新增
❌ 统一任务调度平台                   → 新增（替换现有简单调度）
```

## 2. 成熟产品调研与参考

### 2.1 大厂方案对比

| 维度 | 阿里 DataWorks | 腾讯 WeData | 华为 DataArts Studio |
|------|---------------|-------------|---------------------|
| 核心定位 | 离线数仓 + 数据中台 | 一站式 DataOps 治理 | 政企合规数据治理 |
| 数据集成 | 20+ 源，脚本为主 | 30+ 源，可视化拖拽 | 15+ 源，强元数据 |
| 开发方式 | DAG + SQL，本地 IDE | DAG + SQL/Python，在线 IDE | SQL 为主，低代码 |
| 数据治理 | 依赖 DataWorks + DataQ | 目录 + 血缘 + 质量 + 成本一站式 | 血缘 + 质量 + 标准 |
| 多租户安全 | 组织 + 项目 | 项目空间 + 角色权限 + 资源隔离 | 组织 + 工作组 |
| 参考来源 | [DataWorks 官网](https://www.aliyun.com/product/bigdata/ide) | [WeData 官网](https://cloud.tencent.com/product/wedata) | [DataArts Studio 官网](https://www.huaweicloud.com/product/dayu.html) |

**对 DataHub 的适用性分析**：
- WeData 的 DataOps 理念（数据集成 + 开发 + 运维一体化）最契合我们的全链路设计思路
- DataWorks 的分层建模体系（ODS → CDM → ADS）可作为我们数据分层的参考基准
- 华为的合规治理体系对权限管控设计有借鉴价值
- **不照搬**：大厂方案面向 PB 级数据量，我们需根据实际数据量做减法

### 2.2 开源方案参考

| 项目 | 定位 | 参考点 | 适用性 |
|------|------|--------|--------|
| Apache DolphinScheduler | 任务调度 | DAG 工作流、多租户、告警 | ✅ 可替代现有简单调度，MVP 优先选型 |
| Apache SeaTunnel | 数据集成 | 200+ 连接器、CDC、Schema Evolution | ✅ 可作为多源接入引擎，替代手写适配器 |
| Apache Atlas | 元数据管理 | 血缘追踪、分类、术语表 | ⚠️ 功能重，MVP 可用轻量方案替代 |
| DataX | 离线数据同步 | 插件化架构 | ⚠️ 已被 SeaTunnel 超越，不推荐新项目使用 |

**参考来源**: [Apache DolphinScheduler](https://dolphinscheduler.apache.org/) | [Apache SeaTunnel](https://seatunnel.apache.org/) | [Apache Atlas](https://atlas.apache.org/)

### 2.3 行业分层模型共识

业界通用的数据分层模型为 5 层架构（参考：[华为云 - 数据中台分层建模体系](https://bbs.huaweicloud.com/blogs/310800)）：

| 分层 | 全称 | 职责 | Spider 现状 |
|------|------|------|------------|
| ODS | Operate Data Store | 原始数据存储，业务系统数据镜像 | ✅ 已有 `ts_ods` |
| DWD | Data Warehouse Detail | 明细数据层，轻度汇总 + 维度关联 | ✅ 已有 `ts_dwd` |
| DWS | Data Warehouse Service | 汇总数据层，面向主题聚合 | ✅ 已有 `ts_dws` |
| ADS | Application Data Store | 应用数据层，面向应用的结果数据 | ❌ 需新增 |
| DIM | Dictionary Data Layer | 维度数据层 | ✅ 已有 `ts_dim` |

**Spider 现有但需调整的**：
- `ts_rds`（原始接入层）→ 保留，作为多源数据的统一入口层
- `ts_task`（任务处理层）→ 保留，用于 PDF→Markdown 等 AI 处理任务

### 3.3 优先级决策理由

**P0 选择逻辑**（MVP 必须能跑通完整链路）：
1. 采集层必须支持多源（M01-M04），否则不是"通用"数据中台
2. ETL 分层（M05）是已有能力，只需扩展 ADS
3. 任务调度（M06）是所有数据流的编排核心，必须优先
4. 数据 API（M07）是数据服务化的最小可用形态
5. 管理门户（M08）是用户触达入口

**P1 选择逻辑**（治理与服务深化）：
1. 元数据 + 血缘 + 质量 = 数据治理三件套，让数据可信
2. 指标平台 = 数据服务化的进阶，让指标定义统一
3. 可视化看板 = 数据应用层，让数据可见
4. 监控告警 = 运维保障

**P2 选择逻辑**（精细化运营）：
1. 权限管控是企业级必需，但 MVP 阶段可先用 PG 原生权限
2. 自助分析、报表中心、AI Copilot 是锦上添花
3. 冷热分层需要数据量积累后才有意义

## 5. 数据架构设计

### 5.1 分层模型

| 层级 | Schema | 职责 | 数据来源 | 存储引擎 | Spider 现状 |
|------|--------|------|---------|---------|------------|
| RDS | `ts_rds` | 多源原始数据接入 | 爬虫/API/文件/DB | MongoDB + PG | ✅ 已有 |
| ODS | `ts_ods` | 标准化、去重 | RDS | PG (分区表) | ✅ 已有 |
| TASK | `ts_task` | AI 处理任务 | ODS | PG + MinIO | ✅ 已有 |
| DWD | `ts_dwd` | 明细数据 + 维度关联 | ODS + DIM | PG (分区表) | ✅ 已有 |
| DWS | `ts_dws` | 主题域汇总 | DWD | PG (物化视图) | ✅ 已有 |
| ADS | `ts_ads` | 应用数据 | DWS + DWD | PG + Redis | ❌ 新增 |
| DIM | `ts_dim` | 维度数据 | 手动 + 自动 | PG | ✅ 已有 |

### 5.2 主题域划分

基于 Spider 现有数据特征（卫星/专利/新闻/舆情），规划如下主题域：

| 主题域 | 包含内容 | 数据来源 | 现有适配器 |
|--------|---------|---------|-----------|
| 航天动态 | 卫星发射、轨道数据、太空活动 | satellite_today, planet | ✅ |
| 专利情报 | 专利文献、法律状态、引用关系 | google_patent | ✅ |
| 新闻舆情 | 新闻报道、社交媒体、新闻发布 | blacksky_news, ssc_news, blacksky_posts | ✅ |
| 政策法规 | 政策文件、导航警告 | ssc_press, sealagom_navwarn | ✅ |
| 资源文件 | PDF/图片/文档 | 所有适配器的下载资源 | ✅ |

> **注**: 主题域划分需与 @产品经理-小欣 确认业务需求后调整。

### 5.3 冷热分层策略

| 层级 | 数据特征 | 存储介质 | TTL | 查询频率 |
|------|---------|---------|-----|---------|
| 热数据 | 近 3 个月 | PostgreSQL (SSD) | — | 高（秒级查询） |
| 温数据 | 3-12 个月 | PostgreSQL (HDD) | — | 中（分钟级查询） |
| 冷数据 | 1 年以上 | MinIO (对象存储) | 按需 | 低（小时级查询） |
| 归档数据 | 3 年以上 | 压缩归档 | — | 极低（按需恢复） |

**MVP 版本**：仅实现热数据层（现有 PG），温冷分层在 P2 阶段实现。

### 5.4 存储引擎选型

| 用途 | 引擎 | 理由 | Spider 现状 |
|------|------|------|------------|
| 原始数据缓存 | MongoDB | 文档型，适合非结构化 | ✅ 已有 |
| 结构化数仓 | PostgreSQL + TimescaleDB | 分区表、时序扩展、成熟稳定 | ✅ 已有 |
| 消息缓冲 | Kafka | 高吞吐、分区有序 | ✅ 已有 |
| 文件存储 | MinIO | S3 兼容、低成本 | ✅ 已有 |
| 缓存/去重 | Redis | 高性能键值 | ✅ 已有 |
| 全文检索 | Elasticsearch | 倒排索引、全文搜索 | ✅ 已有（可选） |

> **决策**: MVP 阶段不新增存储引擎，完全基于现有基础设施。

### 6.2 数据层面衔接

```
现有数据流（保留）:
  templates/*.yaml → crawler → MongoDB → syncer → Kafka → ETL(RDS→ODS→TASK→DWD→DWS) → PG

新增数据流（扩展）:
  API 源 ──────────┐
  文件上传 ────────┤
  DB 同步 ─────────┤
                   ├──▶ RDS → Kafka → ODS → ... → DWS → ADS → 数据API
  爬虫（现有） ────┘                                    ↓
                                                  看板/报表/指标
```

### 6.3 配置层面衔接

现有配置使用 `SPIDER_` 前缀环境变量，DataHub 新增配置项：

| 新增配置 | 默认值 | 说明 |
|---------|--------|------|
| `SPIDER_DATAHUB_API_ENABLED` | `true` | 数据 API 服务开关 |
| `SPIDER_DATAHUB_SCHEDULER_TYPE` | `lightweight` | 调度器类型: lightweight / dolphin |
| `SPIDER_DATAHUB_QUALITY_ENABLED` | `false` | 数据质量检查开关 |
| `SPIDER_DATAHUB_LINEAGE_ENABLED` | `false` | 血缘追踪开关 |
| `SPIDER_SEATUNNEL_HOME` | `""` | SeaTunnel 安装路径（DB 同步用） |

## 7. 每个设计决策的验证方式

| 设计决策 | 验证方式 | 验证标准 |
|---------|---------|---------|
| 多源接入 adapter 机制 | POC: 实现 API 源 adapter | 能定时拉取 REST API 数据并写入 RDS |
| ADS 层新增 | POC: 实现 ADS handler | 消费 DWS topic 并生成应用数据表 |
| DAG 任务调度 | 基准测试: 对比 lightweight vs DolphinScheduler | 能编排 10+ 任务的 DAG，支持依赖和重试 |
| 数据 API | POC: 实现 SQL → API 自动发布 | 能通过 API 查询 DWS 层数据 |
| 冷热分层 | 灰度方案: 先对 `ts_dws` 6 个月前数据迁移 | 查询性能下降 < 20%，存储成本下降 > 50% |
| 元数据管理 | POC: 自动采集 PG 表结构 | 能自动发现所有 ETL 层表结构并建目录 |
| 血缘追踪 | POC: SQL 解析生成字段级血缘 | 能解析 ETL handler SQL 并生成血缘图 |

## 8. 与产品经理-小欣的协作交接

### 8.1 需要产品经理确认的事项

| 序号 | 事项 | 类型 | 阻塞级别 |
|------|------|------|---------|
| 1 | 主题域划分是否合理？是否需要新增/调整？ | 需求确认 | P0 |
| 2 | MVP 阶段需要支持哪些具体 API 数据源？ | 需求确认 | P0 |
| 3 | 数据 API 的消费者是谁？有哪些典型查询场景？ | 用户故事 | P0 |
| 4 | 指标平台的指标定义由谁维护？业务方还是技术方？ | 流程确认 | P1 |
| 5 | 可视化看板倾向自研还是集成开源 BI？偏好哪个？ | 技术约束 | P1 |
| 6 | 权限模型是否需要支持行列级？还是表级即可？ | 需求确认 | P2 |
| 7 | 数据脱敏的规则由谁定义？ | 流程确认 | P2 |

### 8.2 技术负责人已做出的约束

| 约束项 | 决策 | 理由 |
|--------|------|------|
| 存储引擎 | MVP 不新增，基于现有 PG/MongoDB/Kafka/MinIO/Redis | 控制基础设施复杂度 |
| 调度引擎 | MVP 用轻量自研 DAG，P2 评估是否引入 DolphinScheduler | 避免过早引入重量级组件 |
| DB 同步引擎 | 评估 SeaTunnel，若集成成本高则自研轻量方案 | SeaTunnel 功能强但部署重 |
| BI 引擎 | P1 阶段集成 Metabase（开源、易部署） | 自研 BI 投入产出比低 |
| 前端框架 | 继续使用 React + Vite | 保护现有前端投资 |
