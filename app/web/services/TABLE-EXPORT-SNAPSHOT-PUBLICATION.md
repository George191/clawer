# Immutable table snapshot publication receiver

The publication pilot is default-off and explicit-local only. Use a **new** PostgreSQL 17+ UTF-8 database on a distinct numeric loopback listener, with a separate owner and dedicated restricted login. It is not the read-only preview or an Upsert/Append receiver. Do not reuse any receiver/sender port, database, login, or marker. Keep database access limited to the owner and publication login. Never point the provisioner at an existing writer, preview or application database.

1. Choose independent random UUIDs for the private receiver marker and deployment revision. Create a separate writer LOGIN with no memberships, role attributes, ownership, or bypass privileges. Revoke database grants from PUBLIC (including TEMP), then grant the writer only database CONNECT. Public must not have schema CREATE.
2. As the owner of the new database, run the standalone `table-export-snapshot-publication-provision.sql` in psql with `ON_ERROR_STOP=1`, `snapshot_writer` set to the login name and `snapshot_marker` set to the new private marker. It grants only schema USAGE, table SELECT, current-generation column UPDATE on the singleton, INSERT on generations/records, and MAINTAIN only on those three tables. The scoped MAINTAIN grant allows a fixed `SHARE UPDATE EXCLUSIVE NOWAIT` lock through commit, fencing concurrent trigger/index/heap DDL without granting owner privileges, DELETE, TRUNCATE, or history UPDATE. It also allows PostgreSQL maintenance on those tables; any physical rewrite invalidates the application pin. It will fail instead of modifying an existing namespace.
3. In an enrollment transaction with `search_path=pg_catalog`, call `await lock_snapshot_publication_relations(connection)` and then `await compute_snapshot_publication_proof(connection)` from `app.web.services.table_export_snapshot_publication_receiver`. Enter the resulting physical enrollment pin in `TABLE_EXPORT_SNAPSHOT_PUBLICATION_PROOF_SHA256`. The attested physical identities include the three built-in heaps and all four native PK/unique B-tree indexes. A rewrite or index rebuild invalidates the pin. If re-enrollment is intentionally authorized, review the physical database and use a new deployment UUID.
4. Configure the local application's `TABLE_EXPORT_SNAPSHOT_PUBLICATION_*` settings including `CONFIG_REVISION` (deployment UUID). Use `ENVIRONMENT=local` explicitly. Never log marker, password, pin, or DSN; the application exposes only an opaque review revision.

Generation zero means no publication. A committed generation is immutable for the writer; only the exact singleton pointer can advance. No application migration, retention timer, deletion script, cleanup or downgrade is provided. Publication history is deliberately retained.
